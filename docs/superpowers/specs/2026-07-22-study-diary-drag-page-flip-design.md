# Study Diary 拖拽式翻页交互设计

**日期**: 2026-07-22
**状态**: 已确认,待写实施计划

## 背景

上一版翻页重设计（`2026-07-22-study-diary-page-flip-redesign.md`）把翻页从简单的 CSS `transition` 换成了带弧形提起 + 透明度渐隐的 `@keyframes` 动画，解决了 Safari 文字/图片破碎的问题，但过程中两次尝试修复"卡顿"（缓动曲线改成 linear、关键帧从两段合并成单峰）都没能彻底解决。用户提出换一种交互方式：**按住页面拖动着翻**，而不是点按钮触发一段固定时长的动画。

这个方向能从根本上绕开"CSS 关键帧动画卡顿"这整条问题线——拖拽翻页时，页面的旋转/位移/透明度直接由指针的实时位置驱动（每次 `pointermove` 直接写 `style.transform`），不经过 CSS `@keyframes` 的时间轴插值机制，所以之前反复出现的"关键帧之间数值/速度不连续"这类问题不会再发生。

## 交互设计

- **保留现状**：上/下一页按钮、键盘左右方向键翻页完全不变，继续使用已经修好的那版 `@keyframes` 动画。拖拽是**新增的**另一种翻页方式，不替代已有方式。
- **触发区域**：跨页视图（宽度 > 768px，与现有 `prefersInstantTransition()` 判断条件一致——窄屏堆叠布局下没有"书脊"可拖，不提供拖拽）下，按住右页任意位置向左拖 = 翻到下一页；按住左页任意位置向右拖 = 翻到上一页。
- **拖动阈值**：按下后位移超过 8px 才判定为"正在拖拽翻页"，避免和页面内其他可点击元素（Discard 按钮、心情/天气按钮、点击图片放大）冲突——普通点击不受影响。
- **松手行为**：拖动进度 ≥ 50% 时松手，顺势自动翻完到下一页；< 50% 时松手，弹回原来那一页。
- **设备支持**：用 Pointer Events（`pointerdown`/`pointermove`/`pointerup`/`pointercancel`）统一处理，鼠标拖拽（桌面端）和触屏手指拖拽（手机/平板）共用同一套代码。
- **边界情况**：已经在第一页时按住左页向右拖、或已经在最后一页时按住右页向左拖——跟现有点击翻页的边界判断（`newIndex < 0 || newIndex >= state.totalPages` 直接不触发）保持一致，`pointerdown` 时就判断没有可翻的下一页/上一页，直接不进入拖拽状态，不会出现"拖出一个空白页"的情况。

## 视觉运动设计

**拖拽进行中**（松手前）：不使用 CSS `@keyframes`，而是每次 `pointermove` 时用 JS 直接计算并写入以下三个值：

- 进度 `progress`（0 到 1）：根据指针水平移动距离相对于页面宽度的比例算出，两端做夹逼（clamp）处理。
- 旋转角度：`progress * 180deg`（"下一页"方向取负值，"上一页"取正值），与进度线性对应，指针走多远纸张转多少。
- 提起高度：`-16px * sin(progress * π)`——用连续的正弦函数而不是固定的几个关键帧数值，保证任意进度下曲线都是平滑连续的，两端（progress=0 或 1）为 0，中间（progress=0.5）达到最大提起高度，不会再出现"数值不变、速度骤停"这种此前卡顿的根源。
- 透明度：`1 - 0.35 * sin(progress * π)`——同样用连续正弦曲线，两端为 1（完全不透明），中间降到 0.65，遮住 Safari 在纸张接近侧面朝向时容易出现的文字/图片渲染破碎问题（沿用上一版设计里验证过的思路）。

**松手结算阶段**（判断是继续翻完还是弹回之后）：改用一次性的 CSS `transition`（只有起点/终点两个状态，不是多段关键帧），从松手时纸张当前的旋转/位移/透明度状态过渡到最终目标状态（完全翻开或完全弹回）。这跟本项目最早期、从未被报告过卡顿的那种"两点式 transition"是同一种机制，所以这一小段结算动画不会重新引入关键帧卡顿问题。

## 技术架构

**新增纯函数**（`js/diary-state.mjs`，可用 `node:test` 自动化测试）：

- `computeDragProgress(startX, currentX, pageWidth)` → 返回 0 到 1 之间夹逼后的进度值。
- `computeFlipVisualState(progress, direction)` → 返回 `{ rotateDeg, liftPx, opacity }`，封装上面的正弦公式（`direction` 决定旋转角度取正还是取负）。
- `shouldCompleteFlip(progress)` → 返回布尔值，判断松手时进度是否达到完成翻页的阈值（≥ 0.5）。

**DOM/手势绑定**（`js/diary.js`，延续本项目"DOM/手势代码不做自动化测试，纯逻辑测"的一贯方式）：

- 现有 `playFlip()` 函数里构建翻页纸张（正反面、阴影元素）的那部分逻辑会抽成一个共享辅助函数，点击/键盘翻页和新的拖拽翻页都调用它来搭建同一套 DOM 结构，避免重复代码。
- 新增指针事件处理：`pointerdown` 时记录起始位置、判断按在左页还是右页决定方向；`pointermove` 时（超过 8px 阈值后）用上面的纯函数算出实时状态并直接写入纸张的 `style.transform`/`style.opacity`；`pointerup`/`pointercancel` 时用 `shouldCompleteFlip` 判断走向，触发对应的一次性 CSS transition 结算，结算完成后更新页面状态（复用现有的 `renderStatic()`/`updateChrome()`）。
- 光标样式：拖拽区域悬停时显示 `cursor: grab`，按下拖动中显示 `cursor: grabbing`，提示这里可以拖动（低成本的可发现性优化）。

## 范围之外

- 不做基于拖动速度的"快速甩动即使没拖过一半也直接翻完"（flick 手势）——按用户确认的"过半才翻完"规则来，不额外加这个复杂度。
- 不限制只能抓页面的一个角落来拖（很多真实翻书 App 只能抓角落模拟卷曲）——整页可拖更符合本项目"不做真正纸张弯曲，只做提起弧线"的既定设计取向，抓取区域越大也越容易被摸到，配合 8px 拖动阈值不会误触其他按钮。
- 不支持触控板/鼠标滚轮横向滚动触发翻页，严格只响应 pointerdown+move+up 这套手势。
- 不改动已有的点击/键盘翻页路径（上一版 `@keyframes` 设计），本次改动是新增，不是替换。
